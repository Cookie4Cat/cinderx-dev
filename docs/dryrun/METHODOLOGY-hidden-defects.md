# 静默缺陷与配置盲区的工程化防线（方法论）

日期：2026-07-09　依据案例：函数死亡看护案（M10 提前 quickening 轮，
MR !46；详细验尸见 M10-early-quicken-log.md 第三节）

## 一、案例摘要

3.11 端口的已编译函数注册表以裸指针（BorrowedRef）为键，其失效
依赖 function watcher（PyFunction_EVENT_DESTROY）——该机制为
3.12+ 专有，3.11 下从不触发。叠加 deopt 路径自伤（注册表持有已
编译闭包的最后强引用，放引即死后继续写对象字段），构成对已释放
内存的越界写。该缺陷自注册表机制引入起即存在，穿透了此前全部
门禁（语义冒烟、差分门禁、引用计数矩阵、libtest、五次全集 A/B），
直至一次非默认阈值（auto=4）的全集测试才以 SIGSEGV 形式曝出。

## 二、隐藏机理：四层掩蔽的叠加

**症状层——分配器地形掩蔽。**对尸体对象的写入仅 4 字节，落点
几乎总在 pymalloc 尚未归还内核的竞技场内：不产生段错误，只静默
污染当前住在该地址的对象。仅当竞技场恰被 unmap 时才升级为可观测
崩溃。症状概率远小于缺陷发生概率，是最危险的缺陷形态。

**触发层——配置单点化（本案主因）。**缺陷前置条件是"存在仅剩
注册表一个强引用的已编译函数"。交付阈值 auto=2 下，asyncio 型
用完即弃闭包（每实例仅一次调用）永远不被编译，触发种群结构性为
空；阈值提高后计数形态改变，种群才出现。十轮验证全部运行于同一
配置点——在被测配置内，无论重复多少次同类测试都不可能发现该
缺陷。这是"测试量"无法弥补、只有"测试维度"能覆盖的盲区。

**观测层——验收器缺口。**崩溃位于解释器关机段（module_free），
基准数值早已采集完成；静默污染态连退出码都干净。既有 oracle
（数值比对、语义分歧、引用计数漂移）均不观测"已释放内存是否被
写"这一维度。

**根因层——移植假设失声。**上游代码携带的 3.12+ 机制假设
（"函数死亡时有人通知"）在 3.11 下无声变假。与 deopt 垫片第四
实参版本门案（MR !42）同族：此类缺陷不依赖代码错误，而依赖
"未被逐项审计的上游默认"。

## 三、方法论原则

1. **配置维度即代码路径。**凡改变"哪些代码被执行/哪些对象群体
   存在"的运行时旋钮（编译阈值、帧模式、特化开关、统计开关），
   均构成独立测试维度；单一配置点意味着该维度的全部盲区。
2. **低概率症状须确定化。**症状概率 ≪ 缺陷概率的类别（UAF、
   越界写、数据竞争）不允许依赖自然暴露，必须以检测器（ASAN 类）
   将其转换为确定性报告。
3. **隐式不变量须台账化。**跨版本移植中，上游的每一项机制默认
   （watcher、回调、生命周期通知）都必须显式记录"3.11 替代机制"
   或"已论证不需要"，缺省即缺陷。
4. **概率性结论须重复化。**堆布局相关的崩溃单跑无判定力；判定
   脚本自身的失败通道（如输出文件冲突）必须与被测失败可区分。

## 四、工程化对策

| # | 对策 | 覆盖掩蔽层 | 落地位置 | 成本 |
|---|---|---|---|---|
| 1 | 配置矩阵门禁 | 触发层 | run_gate/daily | 低 |
| 2 | ASAN 常态化跑道 | 症状层+观测层 | daily/weekly | 中 |
| 3 | PYTHONMALLOC=debug 入门禁 | 症状层（部分） | 现有门禁 | 极低 |
| 4 | 移植假设对照表 | 根因层 | D3 补丁台账 | 低 |
| 5 | 生命周期搅动 corpus | 触发层 | diffgate corpus | 低 |
| 6 | 关机路径断言（debug 构建） | 观测层 | debug 门禁 | 低 |

**1. 配置矩阵门禁。**PR 门禁 = 交付配置全量 + 一个扰动配置的
快档（冒烟 + corpus，扰动轴建议 auto∈{16}）；daily 门禁 = 小
矩阵轮换（auto∈{0,2,16} × early-quicken∈{0,1}，每日一组合）；
每轮性能收口的全集 A/B 附带轮换一个副配置。扰动面用快档控制
成本，核心是让每个旋钮组合以固定周期获得覆盖。

**2. ASAN 常态化跑道。**本案的 UAF 写在 ASAN 下为每次运行确定性
报告——检测器把症状概率拉平为 1。SR3 验收已含 ASAN 项，本案将
其从"待办"升为有实证支撑的必备防线：ASAN 构建 × （冒烟 +
corpus + 异步档）× 配置矩阵，weekly 起步。注意 JIT 可执行内存
分配需 allocator 适配项评估。

**3. PYTHONMALLOC=debug 过渡项。**零构建成本，释放区填充
0xDD + 护栏字节，可捕获部分越界与 API 误用；对本案类 UAF 写
覆盖不全，仅作 ASAN 就位前的廉价过渡，加入冒烟与 diffgate 环境。

**4. 移植假设对照表。**在 D3 补丁台账（[P1]-[P6] 体系）旁增设
"上游机制假设清单"：function/code/type/dict watchers、
sys.monitoring、instrumentation、每项标注 3.11 替代机制或论证。
已覆盖：type watcher（D5 拉式校验）、dict watcher（键版本）、
弱引用 watcher（scope-leak 案）、function watcher（本案死亡
看护）。配套评审规约：任何以 Python 对象指针为键的注册表，必须
写明失效路径（谁、何时、如何注销）。

**5. 生命周期搅动 corpus。**现有 corpus 覆盖语义与引用计数，
不覆盖"编译体的生死周转"。新增 churn corpus：循环量产闭包/
生成器/协程 → 触发编译 → 弃引 → gc.collect → 进程正常退出，
断言干净退出码；配合对策 1 在多阈值下运行，把"asyncio 偶然充当
模糊器"变为常设工位。

**6. 关机路径断言。**debug 构建在 jit::finalize() 入口逐项校验
注册表条目的 weakref 存活性，把静默状态转换为响亮断言；随 debug
门禁运行。

## 五、判定纪律（测试执行侧）

- 崩溃类判定禁止单跑：概率性崩溃（堆布局相关）复验 N≥5，
  记录 P/F 序列而非单一结论；
- 判定脚本的输出通道必须无状态：pyperf `-o` 目标文件复用会以
  报错形式伪装成被测失败，输出文件一律唯一化；
- 修复验证必须包含"修复前可复现、修复后不可复现"的对照，且
  两侧使用同一判定脚本。

## 六、落地优先级建议

1. 对策 3（PYTHONMALLOC=debug）与对策 5（churn corpus）：本周期
   即可入库，改动限于门禁脚本与 corpus 目录；
2. 对策 1（配置矩阵）：改 run_gate 编排，PR 档先行；
3. 对策 4（假设对照表）：一次性整理入 D3 台账，随后进入评审规约；
4. 对策 2（ASAN）与对策 6（debug 断言）：涉及构建口径，随 SR3
   工程化推进落地。
