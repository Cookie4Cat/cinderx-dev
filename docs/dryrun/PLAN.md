# CPython 3.11 适配里程碑预演计划

> 性质：工程预演（dry-run）。在正式开发启动前，以较低的评审强度将 M0–M9 各里程碑
> 快速实现一遍，目的是提前暴露技术风险、校准工作量估算、验证里程碑与 MR 切分的合理性。
> 各里程碑的完成标准降级为：基本功能可运行 + 问题清单 + 实际工时记录。
>
> 产出物范围（预演结束时保留）：补丁清单（每条附理由）、测试资产与基线、
> 问题与风险记录、工时实测数据、预演总结报告。
> **预演代码不直接进入正式开发**；正式开发的 MR 参照预演实现重新编写并接受完整评审。

## 预演必须回答的六个问题

1. vendored ceval.c 所需补丁的数量与规模分布（M2 是唯一没有既有参考实现的区域）；
2. Borrow 清单的实际长度，以及生成管线与手写回退实现的取舍；
3. Lib/test JIT 关闭等价验证的失败项规模与收敛速度（用于外推 M2 的真实工作量）；
4. 正式开发的 6-MR 切分方案是否需要调整；
5. 编码代理在各类里程碑任务上的实际效率数据；
6. 计划外的依赖关系或顺序问题清单。

## 推进顺序（按序推进，不设固定时段）

1. M0：测试门禁资产迁入 + 验证分支差异分析 + 首个 MR（已完成）
2. M1：3.11 wheel 可构建、可安装、可导入（参照验证分支的构建与 Borrow 改动）
3. M2：vendored ceval.c + 补丁 → 26 个核心模块 Lib/test JIT 关闭等价
   （无参考实现区域，弹性最大）
4. M3+M4：frame 基础验证 + 字节码前端（参照验证分支 builder.cpp）→
   完成最小端到端链路（编译→执行→反优化→异常）
5. M5+M6：调用形态矩阵验证 + 反优化/异常正确性验证（重点复核已知缺陷第 0 类）
6. M7+M8：版本号守卫内联缓存（参照验证分支 inline_cache.cpp）+ generator 基础验证
7. M9：pyperformance 性能对比实测 + **预演总结报告**（报告为必交付项，优先级最高）

止损原则：单项受阻时，记录问题清单、降低该项完成标准、继续推进后续项。

## MR 流程约定

- 开发在本仓库（cinderx_oe_311）进行，MR 逐笔合入 cinderx_oe，保留完整轨迹；
- MR 目标分支统一为 `dryrun-311-base`（锚定 kunpeng 仓 dev @75f0f552）；
- 机械性改动（复制、生成）与手工改动分属不同 commit，机械性 commit 的说明中
  注明再生成/校验命令；
- 每个 MR 的描述中附带门禁运行结果摘要（差分门禁 / Lib/test 差分）。
